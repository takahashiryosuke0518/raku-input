# 旧来型フォーム対応 設計仕様

## 目的

既存のChrome拡張「らくらくにゅうりょくん！」を拡張し、標準HTMLフォーム、LabBase型のカスタム年月UI、旧来型のjQuery系フォームを、プロフィールの意味情報に基づく共通ロジックで入力する。今回提示されたサイトのname/idに依存するサイト固有実装は行わない。

## 成功条件

- 既存プロフィールを読み込み、新しい項目が欠けている場合は空値で補完する。
- カナ名・電話・メールを意味のあるプロフィール値として保存し、入力時にフォーム形式へ変換する。
- labelの誤結合、複数の年月項目の混同、電話/メールの無関係な欄への分割を避ける。
- 通常の標準HTMLフォームと既存LabBase対応を維持する。
- 値の設定と必要なイベント発火だけを行う。submit、次へ、保存、登録などは起動しない。

## プロフィール項目とデータ構造

追加する文字列項目:

- `familyNameKana`: カナ姓
- `givenNameKana`: カナ名
- `phoneNumber`: 電話番号
- `mobilePhone`: 携帯電話番号
- `email`: メールアドレス

電話番号は `090-1234-5678` のようなハイフン区切りを基本とし、サイト固有の複数欄形式は保存しない。カナ項目は漢字名・英字名から推測せず、保存値がない場合は空欄として扱う。メールは `example@example.com` のように一つの文字列で保存する。既存の `birthDate` は `YYYY-MM-DD`、年月項目は `YYYY-MM` の文字列を維持する。

保存例:

```json
{
  "profile": {
    "familyName": "山田",
    "givenName": "太郎",
    "familyNameKana": "ヤマダ",
    "givenNameKana": "タロウ",
    "phoneNumber": "",
    "mobilePhone": "090-1234-5678",
    "email": "example@example.com",
    "birthDate": "2002-05-18",
    "gender": "男性",
    "graduationMonth": "2028-03"
  }
}
```

保存層はキーを固定した正規化を続け、未指定キーや未知のキーを保存結果へ漏らさない。旧プロフィールの欠落キーはすべて空文字列（キーワード配列は空配列）となる。

テスト、fixture、ログ、文書の例には実データや実在人物の個人情報を使用せず、上記のような明らかなサンプル値だけを使用する。

## フィールド判定

既存の `collectFieldMetadata` / `classifyControl` とスコア方式を拡張する。情報の優先順位は、対象自身のname/id/placeholder/aria/autocompleteと直接label、入力欄に近接する小さなラベル、`dt`/`th`などの構造化ラベル、fieldset/限定された周辺文脈とする。共通見出しは単独で姓・名やカナ姓・カナ名を決めない。

誤った`label[for]`は参照先が実際の対象inputと一致する場合だけ直接ラベルとして扱う。近接ラベルは同じ小さな親、入力wrapperと隣接するlabel、または限定したancestor内のラベルと対象コントロールの対応が一意な場合に限って採用する。広い親の全`textContent`を各コントロールのラベルとして使わない。複数候補や複数欄で意味が一意に決まらない場合は入力しない。

漢字姓/名、英字姓/名とカナ姓/名を別プロフィールキーに分類する。カナ判定語には「セイ」「姓カナ」「姓（カナ）」「フリガナ（姓）」「ふりがな（姓）」「family name kana」「surname kana」と、対応する名側の語を含める。「カナ氏名」などの共通見出しだけではどちらにも分類しない。

構造化された`dt`/`dd`、`th`/`td`は、関係が同じ行または明示的な対応DOMで一意な場合に利用する。無関係な表セルや広範囲のテキストは参照しない。

radioのlabel取得でも、誤った`for`属性を対象radioへの対応根拠にしない。同一の小さなコンテナ（例: `li`）にradioが1個だけあり、そのコンテナ内の候補labelも1個だけで、隣接グループの他radioと重複・混同しない場合に限り、その兄弟labelを選択肢表示として採用する。複数radioまたは複数labelがあるコンテナでは近接labelを結び付けず、広い親の`textContent`も利用しない。

## 分割入力

項目の意味を先に分類し、その後で部品を決める。コンポーネント語だけで項目のプロフィールキーを推測しない。生年月日、入学年月、卒業年月、研究室開始/終了年月を独立に判定してから year/month/day を割り当てる。属性名（例: birthYear、birthdayMonth、yearOfBirth）も手がかりとするが、label・周辺文脈と組み合わせる。年月の入力先は既存の`YYYY-MM`値から年/月を得る。生年月日の年/月/日は既存の`YYYY-MM-DD`値から得る。各selectは表示文字または値の候補を曖昧なく照合し、実selectの選択状態を更新してinput/changeイベントを発火する。既存の`input[type=month]`とLabBase型カスタム年月入力の経路を維持する。

電話番号・メールアドレスの分割は、入力欄が同一の論理グループに属し、形式が確認できる場合だけ行う。DOM上の近接、同一の小さな行/wrapper、区切り表示（ハイフンまたは`@`）、ラベル/見出しなど複数の根拠を用いる。name/idの並びだけでは分割しない。電話は数字部品の数と順序を確認してからハイフンを除去して分割する。入力欄が1つなら通常どおり保存済み電話番号を入力する。

`phoneNumber`と`mobilePhone`は別項目として厳密に扱い、互いに代用しない。明確に一般の「電話番号」一欄だけがある場合は`phoneNumber`のみを候補とする。`phoneNumber`が空ならその欄を空のままにし、`mobilePhone`へフォールバックしない。携帯電話欄も同様に`mobilePhone`のみを使う。

通常メールは単一の「E-mailアドレス」「メールアドレス」「email」等の欄なら全体を入力する。アカウント部とドメイン部が`@`で区切られることをDOM上で確認できたときだけ分割する。「携帯アドレス」「mobile email」等は`email`の対象外とし、`mobileEmail`をプロフィールに追加しない限り入力しない。確認欄への複製は、「確認」「再入力」「もう一度入力」「confirm」「re-enter」等により確認用であることが明らかな欄だけに同じ値を入力する。単に同じ型や近接した2欄であるだけでは複製しない。

年月/日付のselect optionは、意味が確定したyear/month/day segmentに限り、表示値やoption valueの数値比較で先頭ゼロの差を吸収する（例: `5`と`05`）。この数値正規化を一般のselect値照合に適用しない。

## radio

radio群をnameでまとめ、各radioに紐づくlabel（正しい`for`または内包label）を読む。プロフィールの意味値と表示文字を照合し、サイト固有value（例: `1`、`2`、`M`、`F`）は選択の根拠にしない。

- 男性/男/male → 表示が男性または男の選択肢
- 女性/女/female → 表示が女性または女の選択肢
- その他/その他の性別/other → その他の選択肢

一意に一致する候補だけ選択し、checkedプロパティを更新した上でinput/changeイベントを発火する。既存のselect形式のgender照合も維持する。

## イベントと副作用の保証範囲

値変更後のイベントは既存互換性に必要なcontrolへだけ、標準の`input`/`change`をbubble有効で発火する。無関係なcontrolやラッパーへ追加イベントを発火しない。拡張の処理コードはsubmit/requestSubmit、クリック、フォーム送信、ページ遷移APIを呼び出さない。

合成イベントもページ側のイベントlistenerを実行するため、サイト側スクリプトがイベントから送信や遷移を起こす可能性を、標準イベントを維持したまま一般的に完全防止することはできない。submitイベントを一時的に抑止する仕組みも、`form.submit()`のようなsubmitイベントを経ない呼び出しや、listener内の直接遷移・非同期処理を防げず、正常なサイト動作を壊す恐れがあるため採用しない。この拡張が保証するのは自ら送信・クリック・遷移を呼ばないことまでとする。イベントlistenerが送信/遷移を起こす旧式サイトは実機確認事項とし、安全性を確認できない場合は当該ページでの自動入力を使わない。

## styled native select

select要素自体を第一の信頼できる入力対象とし、ネイティブのselectedIndex/valueを正しく更新してinput/changeイベントを発火する。見た目をjQueryラッパーや独自ウィジェットへ同期させる一般処理は現段階では追加しない。個別サイトに依存するDOM操作はしない。UIラッパーが同期しない場合も、ネイティブselectを更新する範囲を仕様とする。

## 変更予定ファイル

- `profile-storage.js`: 新規プロフィールキーの正規化と後方互換性。
- `popup.html`: カナ姓/名、電話、携帯電話、メールの入力欄。
- `popup.js`: 新規欄の読み書きと入力有無の扱い。
- `autofill.js`: 判定語・近接ラベル収集・日付/年月/電話/メール分割・radio対応。
- `tests/profile-storage.test.js`: 新規キー、欠落キー、未知キーの扱い。
- `tests/popup.test.js`: 新規プロフィール値の表示・保存。
- `tests/autofill.test.js`: 判定・分割・曖昧ケース・イベント・submit非実行。
- `tests/fixtures/test-form.html`: 標準/旧式フォームの手動確認用代表fixture。

`content.js`、`manifest.json`、権限やフォーム送信フローに変更は加えない。

## 追加予定テスト

- 新規プロフィール値のtrimと、旧保存データの欠落項目補完。
- 漢字姓/名とカナ姓/名の近接label判定、誤ったfor属性、共通見出し単独の曖昧判定。
- `dt`/`th`の一意なラベルと、広い親テキストを使わないこと。
- birthDateのdate input/年・月・日select、および各年月項目の年/月select。異なる年月項目を混同しないこと。
- gender radioの日本語/英語表記、独自value、関連labelに基づく選択とイベント。
- 壊れたfor属性でもradio 1個+候補label 1個の小コンテナなら対応し、複数radio/複数labelの曖昧ケースは未変更であること。
- phoneNumber/mobilePhoneの相互フォールバックがなく、emailが携帯アドレス欄に入力されないこと。
- month/dayの意味が確定したselectで`5`と`05`を同値として照合し、一般selectには数値正規化を適用しないこと。
- 電話の一欄入力と、十分な同一グループ根拠がある3分割入力。根拠不足の無関係な欄は未変更。
- メールの単一欄と明示的な`@`区切り、明確な確認欄のみ複製。
- styled native selectのネイティブ選択状態更新とイベント。
- 空プロフィール値、disabled/readonly、候補曖昧、setter失敗、既存LabBase年月、拡張側のsubmit/click非実行。

## 既存機能への影響

プロフィール形状は拡張するが、既存キーと形式を変更しない。旧ユーザーの保存データは新キーが空文字列として正規化される。既存のラテン氏名、prefecture、学校/研究項目、キーワード配列、標準date/month、LabBase型年月の判定・入力を維持する。空プロフィール値はフォームを消去しない。既存同様、判定不能または曖昧な入力はスキップする。値設定処理からフォーム送信やボタン操作を呼ばない。ページ側listenerが合成イベントに反応して行う処理は一般には抑止できないため、実サイトでは別途確認する。

## 実装上のリスクと軽減策

- 古いDOMでlabelとcontrolの対応が弱く、姓/名を取り違える可能性: 限定されたDOM範囲で候補一意性を必須とし、曖昧ならスキップする。
- 日付語と年/月語が同じ行にあることによる項目混同: 項目分類を先に確定し、相反する手がかりや複数候補ではスキップする。
- 電話/メールの複数欄を別項目と誤認する可能性: グループ境界・区切り表記・ラベルを合わせて判定し、name/idのみでは変換しない。
- radioの`for`不整合や日本語表記揺れ: 実ラベル表示を優先し、意味カテゴリごとに一意照合する。
- jQuery UIがネイティブ変更イベントを独自処理に接続していない可能性: native selectの状態と標準イベントを保証範囲とし、サイト固有ラッパー同期を避ける。
- 既存のスコア判定との競合: 既存テストを回帰基準とし、新しい強い証拠が既存の意味判定を上書きしないことをテストする。
- 合成イベントに反応したサイト側の送信/遷移: 標準イベントと互換性を保った完全防止は保証できない。拡張側API非呼出しをテストし、旧式サイトの実機確認事項として利用者へ明示する。

## 明示的な非対象

サイト固有name/idへの依存、フォーム自動送信、submit/次へ/保存/登録ボタン操作、ページ側イベントlistenerが引き起こす任意の副作用の完全防止、iframe/Shadow DOM対応、独自jQueryウィジェットごとの見た目同期、漢字/英字からのカナ生成、mobileEmail。
